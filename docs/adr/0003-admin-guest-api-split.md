# API разделено на гостевое и административное поддеревья

Status: accepted

Контракт (`packages/api/spec/main.tsp`) разделён на два поддерева: гостевое `/api/v1/*` и
административное `/api/v1/admin/*`, с раздельными моделями типов встреч
(`GuestMeetingType` и `AdminMeetingType`, поля пока совпадают). Решение принято наперёд:
список типов и бронирований для владельца может в будущем формироваться иначе, чем для
гостя, — тогда расхождение затронет только своё поддерево и свою модель, а не общий
контракт. Решение родилось в тикете карты «Спека: модель данных и API-контракт» (#7).

## Considered options

- Единое API с общими моделями (`MeetingType`) — отвергнуто: будущее расхождение
  представлений владельца и гостя форкнуло бы общий тип и затронуло обе половины API.
- Отдельные сервисы или порты для админ-части — отвергнуто: избыточно для сервиса с
  одним владельцем и in-memory хранилищем.

## Consequences

- Пути `meeting-types` дублируются в двух поддеревьях (гостевое и админское) — это
  осознанное следствие развязки, а не ошибка копирования.
- Префикс `admin` — структурная развязка контракта, а не защита: авторизации в сервисе
  нет, и до её появления поддерево ничего не охраняет.
- Роутинг сервера и клиентские SDK наследуют разделение: теги `Admin`/`Guest` в OpenAPI
  группируют операции, генерация hey-api разносит их по разным клиентам-функциям.
