# Postgres в проде: Render Blueprint, free-план и ручные миграции

Status: accepted; ревизия — [ADR 0010](0010-migrations-in-deploy.md): миграции применяет entrypoint
контейнера при каждом старте, ручной шаг перед деплоем больше не нужен.

Прод-БД создаётся тем же Blueprint, что и web-сервис `kit-calls`, а сервис получает её internal URL
в `DATABASE_URL`. База — free-план Render Postgres в регионе `singapore`, PostgreSQL 17. Миграции
применяются вручную до появления переменной у сервиса: автозапуска в деплое пока нет. Решение
собрано по тикету [#74](https://github.com/kitXIII/ai-for-developers-project-386/issues/74) как
продолжение [ADR 0008](0008-postgres-drizzle.md) (схема, pg-адаптеры, ручные миграции) и
[ADR 0005](0005-render-docker-deploy.md) (Blueprint, Docker-деплой, free-план).

## Контекст

После #52 приложение умеет работать с Postgres, но прод остаётся на in-memory адаптерах: без
`DATABASE_URL` данные живут в памяти и стираются при каждом сне, рестарте и деплое. Нужен
провижининг БД, которую видит сервис, и способ применять к ней схему. Провижининг Postgres на
Render и `DATABASE_URL` в проде были явно вынесены из #52; автозапуск миграций — в
[#71](https://github.com/kitXIII/ai-for-developers-project-386/issues/71).

## Решение

**БД — часть того же Blueprint.** `render.yaml` получает root-секцию `databases:` с
`kit-calls-db` (`plan: free`, `region: singapore`, `postgresMajorVersion: '17'`), а web-сервис —
переменную:

```yaml
envVars:
  - key: DATABASE_URL
    fromDatabase:
      name: kit-calls-db
      property: connectionString
```

`render.yaml` остаётся источником правды ([ADR 0005](0005-render-docker-deploy.md)); дашборд — только
просмотр. Ресурс не создаётся руками через «New → Postgres», иначе следующая синхронизация
Blueprint его не увидит и инфраструктура разъедется с репозиторием.

**Internal URL и тот же регион.** `fromDatabase.connectionString` даёт internal URL: сервис и БД в
`singapore`, поэтому трафик идёт по приватной сети Render без публичного интернета. External URL
нужен только для ручных миграций с локальной машины и остаётся секретом: в репозиторий и логи он не
попадает.

**Free-план принят осознанно.** Учебному проекту хватает 1 ГБ и 0.1 CPU; платный план не нужен.
Цена — ограничения free-БД: она живёт 30 дней после создания, не поддерживает бэкапы, и активная
free-БД в workspace может быть только одна. Истечение означает апгрейд или пересоздание БД с повторным
`mise run db:migrate`; данные без апгрейда теряются.

**Порядок провижининга — «база → миграции → переменная».** Сначала Blueprint создаёт только БД;
затем схема применяется вручную по external URL; только после этого сервис получает `DATABASE_URL` и
передеплоивается. Если сделать наоборот, приложение поднимется с пустой схемой: старт проверяет
только `SELECT 1`, а таблиц ещё нет. На free web service `preDeployCommand` и one-off jobs
недоступны, поэтому шаг остаётся ручным до #71.

## Considered options

- **Создать БД в дашборде, потом добавить в `render.yaml`** — отвергнуто: до adoption ресурс живёт
  вне Blueprint, а `DATABASE_URL` пришлось бы прописывать вручную; состояние инфраструктуры
  разъезжается с репозиторием.
- **Платный план БД** — отвергнуто: снимает 30-дневный лимит и даёт бэкапы, но для учебного проекта
  не оправдан; при необходимости план меняется без изменения схемы и кода.
- **Поднимать Postgres контейнером рядом с приложением** — отвергнуто: на free-плане нет persistent
  disk, данные всё равно терялись бы; управляемая БД снимает бэкапы и обновления с проекта.
- **Ждать #71 и только потом подключать БД** — отвергнуто: автозапуск миграций не мешает ручному
  шагу, а провижининг разблокирует проверку персистентности и сам #71.
- **`preDeployCommand` в `render.yaml`** — отвергнуто сейчас: Render поддерживает его только на
  платных web-сервисах, а сервис на free-плане; вернуться к варианту можно вместе с #71.

## Consequences

- Прод переживает сон, рестарт и деплой сервиса: данные в Postgres, а не в памяти процесса.
- Free-БД истекает через 30 дней; без апгрейда её пересоздают и заново применяют миграции. Это
  осознанная плата за бесплатный план, а не сбой приложения.
- Схема обновляется только вручную: перед деплоем с новыми миграциями нужно прогнать
  `mise run db:migrate` с external URL. Автоматизация — [#71](https://github.com/kitXIII/ai-for-developers-project-386/issues/71).
- External URL и пароль не коммитятся и не печатаются в логах; в Blueprint хранится только ссылка на
  ресурс, а не строка подключения.
- Регион БД нельзя изменить после создания: `singapore` выбран под текущий web-сервис.
- `DATABASE_URL` читает только `server/index.ts` и передаёт опцией в `buildApp()`; без переменной
  локальная разработка и тесты остаются на in-memory адаптерах ([ADR 0008](0008-postgres-drizzle.md)).
  Ревизия ниже добавляет второй вход — deploy-раннер `server/migrate.ts`.

## Ревизия: миграции в деплое ([ADR 0010](0010-migrations-in-deploy.md))

Утверждение «Схема обновляется только вручную» и порядок «база → миграции → переменная» выше —
принятая история решения до [#71](https://github.com/kitXIII/ai-for-developers-project-386/issues/71).
Теперь `render.yaml` задаёт `dockerCommand: sh -c 'node dist/migrate.js && node dist/index.js'`:
при каждом старте entrypoint применяет журнал из `migrations/` под advisory lock и не пускает
приложение дальше при ошибке. Переменная из Blueprint может существовать с первого деплоя, а пустую
базу доводит до журнала сам entrypoint. `mise run db:migrate` остаётся для локальной БД. Кроме
`server/index.ts`, `DATABASE_URL` читает новый deploy-вход `server/migrate.ts`; приложение
(`buildApp()`) по-прежнему получает URL опцией.
