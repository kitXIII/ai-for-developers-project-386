# Слои серверного API: models, repositories, services, routes

Status: accepted

Серверный API раскладывается на слои с односторонними зависимостями: правила предметной
области живут в моделях, хранение — за асинхронным портом репозитория, сценарии оркестрируют
модели и порты, HTTP-адаптер переводит запросы в вызовы сценариев и доменные ошибки в контракт.
Поведение API снаружи не меняется ни на байт: статусы, коды, тексты, форма ответов и порядок
проверок остаются прежними. Решение собрано по итогам карты «Слои серверного API — models,
repositories, services» ([#18](https://github.com/kitXIII/ai-for-developers-project-386/issues/18))
из резолюций её тикетов; тикеты реализации перечислены в разделе «Порядок реализации и
нарезка».

## Контекст и цель

Сейчас `server/` — плоский набор модулей: роуты импортируют `storage.ts`, `slots.ts` и
`validation.ts` напрямую, доменные правила перемешаны с HTTP-конвертом и форматом моментов,
а `Storage` знает контрактные коды ошибок. Из-за этого нельзя ни заменить in-memory хранилище
на БД без правки роутов, ни протестировать правило, не поднимая Fastify.

Цель — границы, через которые проходит только то, что нужно: домен не знает про HTTP и формат
моментов, сценарии не знают про Fastify, адаптер не переписывает доменные правила и тексты.
Обвязку референса `hexlet-components/js-ddd` (`BaseEntity`/`BaseRepository`/`BaseService`,
`bottlejs`, `validate.js`, `lodash`, `uuid-js`) не берём: нужны границы, а не фреймворк, роль
композиционного корня играет `buildApp()`.

## Целевая раскладка

```
server/
├── models/
│   ├── schedule.ts        Schedule, DEFAULT_SCHEDULE, assertSchedule, MINUTE_MS/DAY_MS, сдвиг пояса
│   ├── errors.ts          DomainError(kind), ни одного statusCode
│   ├── text.ts            общий предикат короткого текста (1–100, без пробелов по краям)
│   ├── meeting-type.ts    инварианты типа встречи, parseMeetingTypeData
│   ├── booking.ts         инварианты имени, draftBooking
│   └── slots.ts           правила ADR 0002 в epoch-ms, assertSlotBookable, busyIntervals
├── repositories/
│   ├── meeting-types.ts   MeetingTypeRepository + inMemoryMeetingTypes()
│   └── bookings.ts        BookingRepository + inMemoryBookings()
├── services/
│   ├── meeting-types.ts   list / get / create
│   ├── bookings.ts        createBooking / listUpcomingBookings
│   └── slots.ts           listSlots
├── routes/                HTTP-адаптер: конверт, +03:00, коды контракта
│   ├── body.ts            конверт запроса: JSON-объект или 400
│   ├── errors.ts          ApiError, errorMap, registerErrorHandler
│   └── …                  по модулю на поддерево API
├── shared/
│   └── moment.ts          formatMoment(ms, schedule)
├── app.ts                 wiring: плагины, зависимости, роуты
└── index.ts               запуск процесса
```

- `models/` — сущности и правила: сетка, окно, пересечения, инварианты значений. Ничего не
  читает само: время, длительность и расписание приходят аргументами.
- `repositories/` — порты и их in-memory адаптеры, по файлу на сущность.
- `services/` — сценарии по возможностям; зависимости приходят явными объектами.
- `routes/` — единственное место, где живут HTTP-статусы, коды контракта и форматирование
  моментов; собирает ответы руками, без отдельного маппера.
- `shared/` — общий для адаптеров код; сегодня это только `formatMoment`.
- `app.ts` и `index.ts` — только wiring: создают адаптеры и часы, регистрируют обработчик
  ошибок и роуты. Кодов и видов доменных ошибок в `app.ts` нет; единственный живущий здесь
  статус — `404` в `setNotFoundHandler` для неизвестных `/api` (резолюция #22): он отвечает
  за SPA-fallback, а не за маппинг доменных ошибок.

`server/errors.ts` и `server/validation.ts` исчезают: `ApiError` переезжает в
`server/routes/errors.ts`, проверка JSON-конверта — в адаптер, инварианты значений — в
умные конструкторы моделей. `server/storage.ts` и `server/slots.ts` умирают вместе с последним
потребителем (раздел «Порядок реализации и нарезка»).

## Порт репозитория

Порт асинхронный с самого начала (`Promise`), даже на in-memory адаптере: переход на БД не
должен переделывать сценарии.

```ts
// server/repositories/meeting-types.ts
export type MeetingTypeRepository = {
  create: (data: MeetingTypeData) => Promise<MeetingType>;
  findById: (id: string) => Promise<MeetingType | null>;
  list: () => Promise<MeetingType[]>;
};

export function inMemoryMeetingTypes(): MeetingTypeRepository;

// server/repositories/bookings.ts
export type BookingRepository = {
  create: (data: BookingData) => Promise<Booking>;
  list: () => Promise<Booking[]>;
};

export function inMemoryBookings(): BookingRepository;
```

- Промах — `null`, а не исключение: «искали и не нашли». `undefined` занят смыслом «поле не
  задано». 404 рождает сценарий (`DomainError('not_found')`), в контракт его переводит адаптер.
- `id` генерирует адаптер (`randomUUID()` в in-memory, схема — в БД-адаптере); отдельного порта
  генерации нет, `create` возвращает сущность вместе с `id`.
- Порядок и фильтры — забота сценария: `list()` отдаёт записи в порядке вставки и ничего не
  обещает о порядке. Отдельных методов под окно или пересечения нет — оба среза одинаково
  дешёвы в памяти, а `listOverlapping` был бы заготовкой под запрос в БД без потребителя.
- `list()` возвращает копию (`[...map.values()]`), не `readonly`-тип и не итератор. Мутация
  возвращённого массива не меняет хранилище.
- `save`/`update`/`clear` в порту нет: редактирования нет (вне скоупа карты), изоляцию тестов
  даёт новый экземпляр на приложение, а не тест-хук.
- Сервисы импортируют только типы портов, `buildApp()` — фабрики. Фабрики, не классы: классы
  в `server/` остаются только у ошибок (`DomainError`, `ApiError`).
- Порты передаются в сценарий по отдельности — `createBooking({ meetingTypes, bookings, schedule,
  now }, input)`, — бандла `Repositories` нет: сценарий перечисляет ровно то, что использует.
- Адаптеры создаются на экземпляр приложения внутри `buildApp()`, не модульным синглтоном.

## Доменные ошибки

`DomainError` несёт вид и текст, но не `statusCode`:

```ts
// server/models/errors.ts
export type DomainErrorKind =
  | 'not_found'
  | 'invalid_value'
  | 'outside_window'
  | 'outside_schedule'
  | 'slot_taken';

export class DomainError extends Error {
  constructor(
    readonly kind: DomainErrorKind,
    message: string,
  ) {
    super(message);
  }
}
```

Виды — 1:1 с кодами контракта, единственный маппинг живёт в `server/routes/errors.ts`:

| `DomainErrorKind`  | Статус | `ErrorCode`              |
| ------------------ | ------ | ------------------------ |
| `not_found`        | 404    | `meeting_type_not_found` |
| `invalid_value`    | 400    | `validation_failed`      |
| `outside_window`   | 409    | `outside_window`         |
| `outside_schedule` | 409    | `outside_schedule`       |
| `slot_taken`       | 409    | `slot_taken`             |

- Текст остаётся вторым аргументом у места броска; адаптер его не переписывает, а только
  переводит вид в пару `{ status, code }`. Один вид может нести несколько текстов:
  `outside_schedule` — выходной / вне сетки / конец дня, `invalid_value` — четыре правила
  значения. Различаются формулировки, а не виды.
- `ApiError` и `errorMap` живут только в `server/routes/errors.ts`; `ErrorCode` из
  `@app/api/types` импортирует на сервере только этот модуль. `Record<DomainErrorKind, …>`
  тотален: новый вид не скомпилируется без строки маппинга.
- Единственный статус вне `routes/errors.ts` — `404` в `setNotFoundHandler` (`app.ts`): он
  отделяет неизвестный `/api` от SPA-fallback (резолюция #22) и с `DomainErrorKind` не связан.
- Адаптер проверяет конверт и свои контрактные поля: тело — JSON-объект, `meetingTypeId` —
  непустая строка, `start` — ISO-момент со смещением. Тип доменного поля — часть его
  инварианта: `parseMeetingTypeData` и `parseGuestName` одним предикатом проверяют и `typeof`,
  и правило, поэтому один текст покрывает «не тот тип» и «не по правилу».
- Замороженный порядок проверок (он наблюдаем снаружи):
  - создание типа: объект → `name` → `description` → `durationMinutes`;
  - бронирование: объект → `meetingTypeId` → `start` → `guestName` → 404 → окно → выходной →
    сетка → конец дня → пересечение.
    Поэтому 400 по имени при неизвестном `meetingTypeId` остаётся 400, а не 404.
- Тексты остаются литералами у места броска и называют дефолтное расписание (14 дней,
  09:00–18:00, UTC+3). Собирать фразу из `Schedule` сейчас не нужно: потребителя нет, а в домен
  приехало бы форматирование чисел и метки пояса. При появлении настраиваемого расписания
  копирайт нужно пересмотреть — связь отмечена комментарием у текстов.

## Настройки расписания и часы

Расписание — один value object из целых минут; модель не читает ни времени, ни конфигурации.

```ts
// server/models/schedule.ts
export type Schedule = {
  utcOffsetMinutes: number; // 180
  workdayStartMinute: number; // 540 (09:00)
  workdayEndMinute: number; // 1080 (18:00)
  windowDays: number; // 14
};

export const DEFAULT_SCHEDULE: Schedule;
export function assertSchedule(schedule: Schedule): void;
```

- Смещение — целые минуты: домен живёт в epoch-ms. Строки (`'09:00'`, `'+03:00'`) заставили бы
  модель парсить формат, IANA-зона потянула бы `Intl` и сломала «UTC+3 круглый год».
- Дефолт задаёт композиционный корень: `buildApp` принимает опцию `schedule` с
  `DEFAULT_SCHEDULE`, симметрично `now`. Отдельного `server/config.ts`, env-переменных и
  конфиг-файла нет — это вне скоупа фичи.
- `assertSchedule` вызывается в `buildApp` до регистрации роутов и падает обычным
  `Error`/`RangeError`: это ошибка конфигурации, а не клиентский ввод. Инварианты: целые минуты,
  `utcOffsetMinutes` в −720…+840, `0 ≤ workdayStartMinute < workdayEndMinute ≤ 1440`,
  `windowDays ≥ 1`. С потолком длительности 540 не связываем: короткий рабочий день легален,
  просто не даёт слотов для длинных типов.
- Модель получает одну входную структуру `{ nowMs, durationMinutes, busy, schedule }`
  (`generateSlots`/`assertSlotBookable`). Сервис получает `schedule` и `now: () => number` в
  зависимостях и вызывает `now()` один раз на сценарий, передавая в модель число. Классов и
  фабрик-замыканий нет — скрытое состояние ничего не инкапсулирует и ухудшает тесты.
- `shared/formatMoment` получает `Schedule` целиком (тип из моделей — намеренная инверсия
  `shared → models`), но читает только `utcOffsetMinutes`: остальные поля расписания ей не нужны.
- Правилами остаются: сетка от `workdayStartMinute` с шагом, равным длительности; хвост дня
  отбрасывается; старт кратен минуте; окно — ровно D+1…D+N календарных дней по локальной дате
  `nowMs`, сегодня не бронируется; выходные Mon–Fri без слотов; непересечение строгое, стык в
  момент окончания разрешён; бронь проверяется теми же правилами. `windowDays` — значение
  настройки, семантика «начиная с завтра» — правило; `firstDayOffset` настройкой не становится.
- Рабочие дни Mon–Fri — правило, а не поле `workdays`: поле расширило бы наблюдаемое поведение
  API без запроса. Появится — отдельным решением с дефолтом.

## Границы слоёв

Границы выражены в [easement.yml](../../easement.yml) плоскими компонентами `server-*` с
allow-list'ом `may_depend_on`; `layers` не трогаем.

```yaml
components:
  server: { in: server } # priority 0: только wiring
  server-routes: { in: server/routes, priority: 1 }
  server-services: { in: server/services, priority: 1 }
  server-repositories: { in: server/repositories, priority: 1 }
  server-models: { in: server/models, priority: 1 }
  server-shared: { in: server/shared, priority: 1 }
```

| Компонент             | `may_depend_on`                                            |
| --------------------- | ---------------------------------------------------------- |
| `server`              | `api` + явный перечень пяти слоёв                          |
| `server-routes`       | `api`, `server-services`, `server-models`, `server-shared` |
| `server-services`     | `api`, `server-repositories`, `server-models`              |
| `server-repositories` | `api`, `server-models`                                     |
| `server-models`       | `api`                                                      |
| `server-shared`       | `api`, `server-models`                                     |
| `tests`               | `api`, `server` + явный перечень пяти слоёв                |

- `components` в easement плоская: владельца файла выбирает `(priority, длина in-паттерна)`,
  иерархии нет. `priority: 1` и длина паттерна отдают вложенные файлы слоям без `except`;
  `optional: true` не нужен — все каталоги появляются в том же изменении, что и конфиг.
- У `server` — явный перечень, не глоб `'server-*'`: новый слой требует осознанного grant.
- `server-shared → server-models` — намеренная инверсия: `formatMoment(ms, schedule)` берёт тип
  `Schedule` из моделей. `server-services` `server-shared` не получает: форматирование момента —
  забота адаптера.
- `tests: auto` остаётся, но `may_depend_on` перечисляет `api`, `server` и пять слоёв явно, без
  глоба `server*`: глобы в списках компонентов появились только в easement 0.6.6, а версия
  инструмента запинена в `mise.toml`, чтобы локальная и CI-сборка совпадали. Колокация тестов
  рядом с кодом тоже попадает в `tests` (priority 1 000 000).

Три «нет»:

- **Без `common`**: общий компонент выдаёт разрешения всем, и `client → server/shared`
  становится `allowed by common` — граница «SPA не ходит в сервер» пробита. `server-shared`
  перечисляется только у `server-routes`.
- **Без `public` и баррелей**: `public` работает, но требует `index.ts` в каждом слое и делает
  перенос модуля внутри слоя публичным изменением. Границу держат компоненты, внутри слоя
  импортируем модули напрямую.
- **Без `surfaces`**: поверхности задают границы внутри одного компонента и не могут запретить
  `services → routes`.

`layers` остаётся `[client, server]` + `api`: это не только запрет, но и источник разрешений —
вложенные `server-*` в `layers` разрешили бы `client → server-services`.

Пять `examples` в конфиге — пины политики, `check` судит их без кода:

- `server/services/x.ts → server/routes/x.ts`: `rejected` — HTTP — забота адаптера;
- `server/models/x.ts → server/repositories/x.ts`: `rejected`;
- `server/routes/x.ts → server/repositories/x.ts`: `rejected` — слой не перескакиваем;
- `client/x.ts → server/models/x.ts`: `rejected` — страховка от будущего `layers`-grant;
- `test/server/x.test.ts → server/services/x.ts`: `allowed` — страховка, что `tests`-глоб не сузят.

Конфиг и перенос файлов — одно изменение (PR фичи): на текущем плоском `server/` конфиг даёт
цикл `server → server-routes → server` и нарушения на `storage.ts`/`slots.ts`/`validation.ts`.
`easement.baseline.yml` не перегенерируем и не пополняем, `--accept-new` не используем,
`easement:disable` не добавляем. Если `check` падает — чиним код (перенос или разворот
зависимости), а не конфиг. `because` в конфиге — по-английски, как весь файл.

## Стратегия тестов

У каждого слоя свой оракул — то, чего не может доказать другой слой. Контрактный тест и e2e
остаются оракулом «снаружи заморожено» и не меняются.

| Слой        | Файлы                                                           | Доказывает                                                                                                                     | Не доказывает                                                       |
| ----------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| Контракт    | `test/api/contract.test.ts` — без изменений                     | форму и поведение API, статусы/коды, сортировку предстоящих, инжектированные часы                                              | порядок правил, отсутствие записи после ошибки, границы инвариантов |
| Модели      | `test/server/models/*.test.ts`                                  | правила значений, сетку/окно/пересечения, приоритет правил                                                                     | HTTP, формат моментов, хранилище                                    |
| Репозитории | `test/server/repositories/in-memory.test.ts`                    | контракт порта: id, промах → `null`, порядок вставки, копию массива                                                            | сценарии                                                            |
| Сценарии    | `test/server/services/*.test.ts`                                | оркестрацию: 404 раньше правил слота, «после ошибки не записали», `endMs`, фильтр и порядок предстоящих, `busy` из всех броней | коды/статусы, формат `+03:00`, конверт                              |
| Адаптер     | `test/server/shared/moment.test.ts` + `test/server/app.test.ts` | форматирование момента по настройкам; JSON-404 неизвестных `/api`                                                              | маппинг вид → статус/код (его держит контракт)                      |
| e2e         | `test/e2e/*` — без изменений                                    | пользовательские пути через UI                                                                                                 | всё остальное                                                       |

- Фейкового репозитория второго образца нет: в тестах сценариев берутся продовые
  `inMemoryMeetingTypes()`/`inMemoryBookings()`, новые на каждый тест, сиды — через `create()`.
  Никаких `vi.fn`, `vi.mock` и проверок количества вызовов: запись наблюдается через `list()`.
- Модель остаётся целиком в epoch-ms: `generateSlots` отдаёт `dayStartMs`, строки и `+03:00`
  собирает адаптер (`formatMoment(dayStartMs, schedule).slice(0, 10)`). `slots.test.ts`
  переезжает в `test/server/models/slots.test.ts` с ожиданиями в epoch-ms; кейс про
  сериализацию `+03:00` уходит в тест адаптера.
- Инварианты моделей проверяются матрицей `it.each` только по `kind === 'invalid_value'`:
  точные тексты не пиннятся — копирайт не должен ломать тест. Порядок внутри одного вида
  (`outside_schedule`: выходной / сетка / конец дня) снаружи ненаблюдаем без пиннинга текста —
  осознанный компромисс, а не пробел.
- `assertSchedule` остаётся без тестов: расписание приходит только из кода `buildApp`, дефолт
  валиден, а тест `buildApp({ schedule: плохое })` дублировал бы строку вызова. Появится внешний
  источник настроек — появится и тест.
- Общие фикстуры — `test/server/fixtures.ts`: `FROZEN_NOW_MS`, `TEST_SCHEDULE` (литералы, не
  импорт `DEFAULT_SCHEDULE` — иначе тест проверял бы сам себя), `ms()`, `localDate()`,
  `seedMeetingType()`. Часы везде — `now: () => FROZEN_NOW_MS`, без `vi.useFakeTimers`.
  Колокация исключена: `vitest.config.ts` берёт только `test/**/*.test.ts`.
- `docs/test-plan.md` получает разделы «Юнит (модели)», «Юнит (сценарии)», «Юнит
  (репозитории)», «Юнит (адаптер: момент)»; отметки ставятся в том же коммите, что и тесты.

## Шов часов

`test/api/contract.test.ts` инжектирует часы строкой (`now: () => '2026-11-16T12:00:00+03:00'`,
в admin-списке — мутабельной), а домен живёт в epoch-ms. Контрактный тест — замороженный оракул
и не правится, поэтому шов такой: **`buildApp` продолжает принимать `now: () => string`, wiring
конвертирует в `() => number`** (`Date.parse(now())`). Домен и сценарии видят только числа,
контрактный оракул остаётся байт-в-байт.

## Порядок реализации и нарезка

Режем вертикальными срезами по возможностям, а не слоями снизу вверх: `knip` валит коммит, где
`server/models/*` ещё без потребителя, а слоистая симметрия требует временных шимов. Правило
удаления: **старый модуль умирает в том же коммите, где переехал его последний потребитель**.
Две реализации одного и того же (два алгоритма слотов, две валидации имени одновременно)
запрещены; сосуществование старого с новым в ещё не перенесённой возможности разрешено —
`storage.ts` один на все роут-модули.

Форма поставки — один PR фичи, шаг = коммит. Порядок:

1. [Слои: типы встреч — модель, порт и сценарии](https://github.com/kitXIII/ai-for-developers-project-386/issues/30):
   `DomainError`, инварианты типа встречи, порт типов, сценарии, `routes/errors.ts` с
   единственным маппингом.
2. [Слои: брони — модель, репозиторий, создание и список предстоящих](https://github.com/kitXIII/ai-for-developers-project-386/issues/31):
   `Schedule` + `assertSchedule`, `formatMoment`, модель брони, `assertSlotBookable`, порт
   броней, `createBooking` + `listUpcomingBookings`, часы в epoch-ms; умирают `storage.ts` и
   `validation.ts`.
3. [Слои: календарь слотов — модель, сценарий, адаптер](https://github.com/kitXIII/ai-for-developers-project-386/issues/32):
   `generateSlots` в epoch-ms с `dayStartMs`, `listSlots`, сериализация `+03:00`; умирает
   `server/slots.ts`.
4. [Слои: гейт easement и абзац в AGENTS.md](https://github.com/kitXIII/ai-for-developers-project-386/issues/33):
   плоские `server-*`, матрица `may_depend_on`, пять `examples`, абзац в `AGENTS.md`; продовый
   код не меняется.

Рёбра: этот ADR → типы встреч → брони → календарь → гейт.

Критерий готовности каждого шага: `mise run check` зелёный целиком (включая e2e и `easement`),
`test/api/contract.test.ts` и `test/e2e/*` — ноль диффа, `gen:check` чистый, нет неиспользуемых
экспортов (`knip`) и тест-хуков в продовом коде, `easement.baseline.yml` не перегенерирован,
публичное поведение API не изменилось. Приёмка всей фичи: подмена in-memory адаптера на другой
не трогает `models/` и `services/` — сценарии зависят только от типов портов, `server-models`
умеет зависеть только от `api`, а `server-services` не видит `server-routes`.

## Атомарность «проверил → записал» при переходе на БД

In-memory адаптер не даёт гонок: проверка слота и запись происходят в одном потоке. С БД между
`list()` и `create()` появляется окно, поэтому фиксируем направление заранее: **модель проверяет
правила, `create` пишет, уникальность обеспечивает схема БД**. Атомарность даёт составной
уникальный индекс по интервалу/слоту плюс обработка нарушения ограничения в адаптере, а не
транзакция вокруг сценария. Кодом сейчас не реализуем: БД вне скоупа этой фичи, решение нужно
только чтобы форма порта и границы слоёв не мешали будущему адаптеру.

## Considered options

- Слои снизу вверх (сначала все модели, потом все репозитории) — отвергнуто: `knip` валит
  промежуточные коммиты, а слоистая симметрия требует временных шимов. Вертикальные срезы
  по возможностям дают зелёный `check` на каждом шаге.
- Иерархия компонентов easement (`server/routes` под `server`) — отвергнуто: `components`
  плоская, вложенность эмулируется перекрытием `in`, а `layers` с вложенными `server-*`
  начинает выдавать разрешения вниз (`client → server-services`).
- `common` для общего кода — отвергнуто: выдаёт разрешения всем компонентам и пробивает
  границу `client → server`.
- `public` и баррели на слоях — отвергнуто: перенос модуля внутри слоя становится публичным
  изменением, а границу и так держат компоненты.
- Каталог текстов ошибок в адаптере — отвергнуто: потребовал бы дискриминатор поля/причины в
  домене и переоткрыл бы решение «различаются сообщения, не виды».
- Синхронный порт репозитория (как `createStorage()`) — отвергнуто: БД-адаптер заставил бы
  переделывать все сценарии.
- `Storage`-бандл или `RouteOptions` — отвергнуто: сценарий должен перечислять ровно те
  зависимости, которые использует; сборка — в `buildApp()`.
- Собирать тексты ошибок из `Schedule` — отвергнуто: дефолты дают те же байты, но в домен
  приезжает форматирование чисел и метки пояса, а потребителя нет.

## Consequences

- Границы проверяются статически: `easement check` в `mise run check` и на pre-push. Нарушение
  чинится переносом кода или разворотом зависимости, а не правкой конфига.
- `AGENTS.md` получает абзац про плоские `server-*` и направление
  `wiring → routes → services → repositories → models`, `shared → models`, `api` всем слоям,
  плюс правило: не добавлять `server-*` в `layers`, не заводить `common` для слоёв, новый
  слой — новый компонент и явный `may_depend_on` (шаг 4 нарезки).
- In-memory адаптер заменяется на БД без правки моделей и сценариев: порт уже асинхронный,
  `id` и порядок — забота адаптера и сценария соответственно.
- Доменные тексты — литералы, знающие дефолтное расписание; при появлении настраиваемого
  расписания копирайт пересматривается.
- `assertSchedule` не покрыт тестами: расписание приходит только из кода `buildApp`. Внешний
  источник настроек — повод завести тест.
- `GLOSSARY.md` не меняется: слои — реализация, а не предметная область.
