# Postgres через Drizzle: схема, exclusion constraint и ручные миграции

Status: accepted; ревизия — [ADR 0010](0010-migrations-in-deploy.md): в проде журнал применяет
entrypoint контейнера до старта приложения, `dist/index.js` по-прежнему не мигрирует.

Без `DATABASE_URL` приложение работает как раньше: in-memory адаптеры и неизменное поведение API. С
непустым `DATABASE_URL` оба порта репозиториев идут в Postgres через один `pg.Pool` и один
Drizzle-инстанс. Схема живёт в слое `repositories`, миграции — в корневом `migrations/` и
применяются только вручную (`mise run db:migrate`); приложение никогда не мигрирует себя само.
Инвариант «нет пересекающихся броней» обеспечивает exclusion constraint, а не транзакция вокруг
сценария. Решение собрано по тикету
[#52](https://github.com/kitXIII/ai-for-developers-project-386/issues/52) как продолжение
[ADR 0004](0004-server-layers.md) (слои, порты и «Атомарность „проверил → записал“») и
[ADR 0006](0006-composition-without-di-container.md) (композиция без DI-контейнера).

## Контекст и цель

Состояние жило в памяти процесса: типы встреч и брони терялись при рестарте, а порты репозиториев
имели только in-memory адаптеры. `DATABASE_URL` не читался, Postgres и Drizzle отсутствовали в
зависимостях.

Цель — сохранять данные, не меняя ни снаружи API, ни внутри границ слоёв: модели и сценарии знают
только порты из ADR 0004, HTTP-адаптер и тексты не трогаются, контрактные и e2e-тесты остаются
оракулом «снаружи заморожено» и работают без базы. Тесты pg-адаптеров не должны требовать Docker
или внешнего Postgres, поэтому проверяются на PGLite — том же Postgres, собранном в WASM.

## Решение

**Drizzle ORM + `pg`.** Схема описывается TypeScript-кодом рядом с адаптерами, запросы остаются
типизированными и близкими к SQL, а `drizzle-kit` генерирует обычные SQL-миграции, которые можно
ревьюить. Prisma принесла бы свой движок и генератор, Kysely — отдельный язык описания схемы;
Drizzle закрывает и схему, и запросы, и миграции без второго источника правды.

**Один пул и один Drizzle-инстанс на приложение.** `composeDependencies()` (ADR 0006) —
единственное место, знающее конкретные адаптеры: при заданном URL он создаёт `pg.Pool`, оборачивает
его в `drizzle(pool, { schema })` и отдаёт оба pg-адаптера, `checkConnection` и идемпотентный
`close`. В приложении `process.env.DATABASE_URL` читает только `server/index.ts`; `buildApp()` и
композиция получают URL опцией, поэтому тесты и другие встраивания не наследуют БД деплоя. Пустая
строка эквивалентна отсутствию переменной. Тот же `process.env.DATABASE_URL` читает
`server/repositories/drizzle.config.ts` — только для CLI `drizzle-kit` (генерация миграций и
`migrate`), никогда в рантайме приложения.

**Схема.** Две таблицы, по одной на сущность:

- `meeting_types`: `seq bigint generated always as identity`, `id uuid primary key default
  gen_random_uuid()`, `name`, `description`, `duration_minutes`;
- `bookings`: тот же `seq` и `id`, `meeting_type_id uuid` с FK на `meeting_types.id`,
  денормализованное `meeting_type_name`, `guest_name`, `start_ms`/`end_ms` в `bigint`.

`id` генерирует БД, поэтому контракт порта «`create` возвращает сущность с id» один и тот же для
обоих адаптеров. `seq` — монотонная identity-колонка, а не первичный ключ: Postgres не обещает
порядок строк без `ORDER BY`, а `list()` по контракту отдаёт записи в порядке вставки. Время —
epoch-ms, как во всём домене (ADR 0004); `bigint` хранит его без потери точности и позволяет
построить по интервалу exclusion constraint. Имя типа денормализовано осознанно: типы не
редактируются и не удаляются, поэтому копия не устаревает, а читать бронь можно без join.

**Инвариант непересечения — в схеме.** Drizzle не умеет exclusion constraints первоклассно, поэтому
вторая миграция — custom SQL:

```sql
ALTER TABLE "bookings" ADD CONSTRAINT "bookings_no_overlapping_slots"
  EXCLUDE USING gist (int8range("start_ms", "end_ms") WITH &&);
```

`int8range` по умолчанию полуоткрытый (`[start, end)`), поэтому стык разрешён: бронь, начинающаяся в
момент окончания предыдущей, проходит. Отклоняются одинаковый старт, частичное наложение и любые
разные длительности — уникальный индекс здесь не годится, потому что пересечение не является
равенством ключа. Нарушение приходит с SQLSTATE `23P01` (`exclusion_violation`); адаптер переводит
только его в `DomainError('slot_taken', 'errors.domain.slots.taken')`, остальные ошибки (например,
`23503` от FK) пробрасывает как есть. Drizzle оборачивает ошибку драйвера, поэтому код ищется по
цепочке `cause`.

**Шов драйверов.** Прод-адаптер и тестовый — один код: фабрики принимают
`PgDatabase<TQueryResult extends PgQueryResultHKT, typeof schema>`, где generic — тип результата
драйвера. `drizzle-orm/node-postgres` подставляет `NodePgQueryResultHKT`, `drizzle-orm/pglite` —
`PgliteQueryResultHKT`, поэтому дублировать адаптер под драйвер не нужно, а типы `select`/`insert ...
returning` остаются выведенными. `tsc` проверяет оба инстанцирования.

**Миграции — руками.** SQL лежит в корневом `migrations/` вместе с журналом Drizzle, конфиг —
`server/repositories/drizzle.config.ts` рядом со схемой (пути в нём корневые: `drizzle-kit` считает
их от рабочего каталога). Генерация: `drizzle-kit generate`, кастомная миграция для constraint —
`drizzle-kit generate --custom`. Применение: `mise run db:migrate`, который требует `DATABASE_URL`
и падает с понятным сообщением, если переменной нет. Автоприменения на старте нет: несколько
инстансов не должны гонять миграции, старт не должен менять схему, а файлы миграций пока не
попадают в runtime-образ (follow-up [#71](https://github.com/kitXIII/ai-for-developers-project-386/issues/71)).

**Старт и жизненный цикл.** С `DATABASE_URL` `buildApp()` до регистрации роутов выполняет
`SELECT 1`; неудача закрывает пул и отклоняет промис, поэтому `listen` не запускается, а
`server/index.ts` логирует ошибку и завершается с ненулевым кодом. `app.close()` закрывает пул через
`onClose`; повторный `close` возвращает тот же промис. Для in-memory адаптеров `checkConnection` и
`close` — no-op, поэтому путь без базы не приобретает ни проверки соединения, ни утечек.

## Тесты

- Общий контракт портов (`test/server/repositories/suite.ts`) прогоняется на in-memory и на PGLite:
  id, промах `findById` → `null`, порядок вставки, копия массива. Сиды идут через порт, брони
  ссылаются на настоящий `meeting_type_id` — иначе FK в Postgres не пройдёт.
- PGLite: один экземпляр на файл, миграции применяются один раз (и второй раз, чтобы зафиксировать
  идемпотентность), перед каждым тестом
  `TRUNCATE TABLE bookings, meeting_types RESTART IDENTITY CASCADE`.
- Ограничения схемы проверяются на уровне адаптера: одинаковый старт, частичное наложение разных
  длительностей, одинаковый старт разных длительностей → `DomainError('slot_taken')`; стык
  разрешён; нарушение FK — не `DomainError`.
- Контрактный тест и e2e не меняются: они строят приложение без URL и остаются на in-memory
  адаптерах.

## Considered options

- **Автоприменение миграций на старте** — отвергнуто: гонки нескольких инстансов, изменение схемы
  при старте и отсутствие `migrations/` в образе; ручной шаг делает состояние схемы явным.
- **`drizzle-kit push` вместо миграций** — отвергнуто: нет истории и ревьюимого SQL, а diff
  схлопывается в необратимое «привести базу к коду».
- **Транзакция с `SERIALIZABLE` вокруг сценария** — отвергнуто: атомарность пришлось бы проводить
  через порт (`list()` + `create()` в одной транзакции), порт знал бы о транзакциях, а конфликт
  всё равно выражался бы ошибкой сериализации. Exclusion constraint закрывает окно на уровне того,
  что защищаем — интервала.
- **Уникальный индекс по старту или по паре старт/длительность** — отвергнуто: пересечение
  интервалов не сводится к равенству ключа; частичное наложение разных типов прошло бы.
- **Отдельный адаптер на каждый драйвер** — отвергнуто: два одинаковых набора запросов разошлись бы
  при первом изменении; generic по `PgQueryResultHKT` даёт один код.
- **Тесты на внешнем Postgres (Testcontainers)** — отвергнуто: Docker в CI и локально стал бы
  обязательным; PGLite — тот же Postgres, транзакции и constraints работают идентично.
- **Вынести схему в отдельный слой или пакет** — отвергнуто: схема — деталь хранения, её читает
  только `server-repositories`; новый слой потребовал бы правок `easement.yml`.

## Consequences

- Прод-поведение по умолчанию не меняется: без `DATABASE_URL` всё как раньше. Провижининг Postgres
  на Render, `DATABASE_URL` в проде и деплой — вне скоупа #52.
- Копирование `migrations/` в runtime-образ и deploy-раннер — follow-up
  [#71](https://github.com/kitXIII/ai-for-developers-project-386/issues/71); до него прод остаётся
  на in-memory.
- Порядок `list()` — обязательный `ORDER BY seq`; удаление строк не переиспользует номера, но и не
  нарушает порядок оставшихся.
- PGLite — один поток и фиксированная версия Postgres из пакета; SQL миграций держим стандартным,
  без расширений вроде `btree_gist` (range-операторы `&&` есть в ядре).
- Один пул на приложение: тесты, создающие приложение, обязаны его закрывать, иначе пул держит
  процесс.
- `knip` узнаёт конфиг Drizzle через плагин `drizzle` в `knip.json`; конфиг остаётся файлом слоя
  `repositories`, а `easement.yml` не меняется.

## Ревизия: миграции в деплое ([ADR 0010](0010-migrations-in-deploy.md))

Разделы «Миграции — руками» и «Автоприменения на старте нет» выше — принятая история решения до
[#71](https://github.com/kitXIII/ai-for-developers-project-386/issues/71). Теперь образ содержит
`migrations/`, а entrypoint контейнера (`dockerCommand` в `render.yaml`) запускает
`dist/migrate.js` перед `dist/index.js`: журнал применяется под advisory lock, ошибка блокирует
старт. `mise run db:migrate` остаётся для локальной БД, а `buildApp()`/`dist/index.js` схему
по-прежнему не меняют. Вариант «автоприменение на старте» из списка отвергнутых заменён осознанно:
на free-плане Render нет другой точки запуска, а отдельный entrypoint не смешивает миграции с
HTTP-приложением.
