# Единственный адаптер хранилища: Postgres, PGlite вне прода

Status: accepted

In-memory адаптеры репозиториев удалены: у портов остался один адаптер — Postgres. Прод работает
через `pg`, локальная разработка, vitest и e2e — через PGlite (тот же Postgres, собранный в WASM и
живущий в памяти процесса). Выбор хранилища передаётся в `buildApp()` явно
(`database: { kind: 'postgres', url } | { kind: 'pglite' }`), а решение принимает `server/index.ts`:
явный `DATABASE_URL` — Postgres, иначе `--dev` — PGlite, иначе процесс падает при старте. Решение
собрано по тикету
[#85](https://github.com/kitXIII/ai-for-developers-project-386/issues/85) как ревизия
[ADR 0008](0008-postgres-drizzle.md).

## Контекст

После ADR 0008 у портов было два адаптера: in-memory и Postgres. Память оставалась дефолтом без
`DATABASE_URL`, поэтому вторым способом хранения пользовались dev, HTTP-тесты и все e2e, а сценарии
и схема проверялись раздельно: тесты сценариев не видели ни внешнего ключа, ни exclusion constraint
и принимали любые значения. В проде (ADR 0009, ADR 0010) память не использовалась, но отсутствие
переменной продолжало означать «тихо отдать пустой сервис».

## Решение

- **Один адаптер.** `server/repositories/` содержит порты, pg-адаптеры, схему и две сборки
  хранилища: `postgres-persistence.ts` (прод) и `pglite-persistence.ts` (локально и в тестах).
  `Persistence` — связка обоих портов плюс `checkConnection` и `close`.
- **PGlite — тот же Postgres.** Один и тот же `postgresMeetingTypes`/`postgresBookings` работает на
  обоих драйверах, поэтому внешний ключ, exclusion constraint и порядок `list()` проверяются в
  тестах так же, как в проде.
- **Явный шов.** `buildApp({ database })` без значения по умолчанию; `composeDependencies()` стал
  асинхронным и сам поднимает выбранное хранилище. «Нет базы» перестало быть вариантом.
- **Политика входа.** `server/index.ts`: непустой `DATABASE_URL` — Postgres; иначе `--dev` —
  PGlite; иначе сообщение в stderr и `exit 1`. Явная переменная важнее флага, поэтому
  `DATABASE_URL=… pnpm dev` продолжает работать на настоящем Postgres.
- **PGlite в памяти и с авто-миграцией.** База стартует пустой, журнал применяется при создании,
  данные умирают вместе с процессом. Правило «приложение не мигрирует» (ADR 0010) относится к базе,
  которая переживает деплой, а не к эфемерной.
- **Ленивый импорт.** `@electric-sql/pglite` остаётся в `devDependencies`: `dist` пакета — 26 МБ
  (wasm 9,1 МБ), а runtime-стадия образа ставит только `--prod`. Модуль подгружается через
  `import()` на PGlite-ветке, поэтому в прод-образ не попадает.
- **Изоляция тестов.** `createTestPersistence()` поднимает свежий PGlite на каждое приложение и
  каждый тест сценария: «новый `buildApp()` = пустые данные» сохраняется дословно, чистить таблицы
  не нужно.

## Рассмотренные варианты

- **Оставить in-memory адаптеры только для тестов** — отвергнуто: это второй способ хранения,
  который надо поддерживать, и тесты сценариев снова не видят схему.
- **Настоящий Postgres везде, включая тесты (Testcontainers)** — отвергнуто по причине ADR 0008:
  Docker стал бы обязательным в CI и локально.
- **PGlite в `dependencies` со статическим импортом** — отвергнуто: 26 МБ в прод-образе ради
  профиля, которого в проде нет.
- **PGlite в файле для dev** — отвергнуто: нужен каталог данных, отдельная копия на каждый процесс
  e2e и защита от устаревшей схемы. Долговечные локальные данные доступны через `DATABASE_URL`.

## Последствия

- Приложение без `DATABASE_URL` и без `--dev` не стартует; локальный `docker run` требует
  переменную, и `mise run docker:run` её пробрасывает.
- Dev-данные по-прежнему теряются при рестарте — теперь их хранит PGlite, а не адаптер в памяти.
- Suite подорожал: PGlite boot ≈ 0,6 с на инстанс, `pnpm test` — с ~2 с до ~10 с.
- ADR 0008 в части in-memory-дефолта заменён; ADR 0009 и ADR 0010 сохраняют силу, но их фразы про
  in-memory-поведение устарели (отмечено в их статусах).
